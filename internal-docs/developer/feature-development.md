# 機能開発

Web、API、DBをまたぐ機能を追加するときの基本方針です。

## 実装順序

1. データと権限の境界を決める
2. 必要ならDBマイグレーションを追加する
3. WebとAPIで共有する型を更新する
4. APIの入力検証と処理を実装する
5. WebのAPI wrapperを実装する
6. UIを実装する
7. テストと必要なドキュメントを更新する

## データと権限

実装前に次を決めます。

- どのしおりに属するデータか
- 閲覧者へ返すか、編集権限が必要か
- 公開向けの表示へ含めるか
- コピー時に引き継ぐか
- 削除時に関連データをどう扱うか
- 予定や旅行メンバーなど他のデータを参照するか
- 金額、日時、URL、JSONなどへどの検証が必要か

## DB

スキーマの正本は`apps/db/migrations/sql/`です。適用済みマイグレーションは変更せず、新しいマイグレーションを追加します。

```bash
make migrate-new name=add_feature
make migrate-up
```

## 共有型

WebとAPIで共通する入力、レスポンス、定数は`packages/types/`へ置きます。DB固有の表現はAPI境界でWeb向けの型へ変換します。

## API

入力はZodなど既存の検証方法を利用し、routeとserviceの責務を分けます。

新しいrouteを追加した場合は、APIのエントリーポイントから明示的に登録されていることを確認してください。

アカウント認証としおり編集認証は用途が異なります。endpointごとに必要な認証方式を明確にしてください。

## Web API wrapper

WebからAPIへアクセスするときは`apps/web/src/lib/api/`の既存パターンに合わせます。URL、認証ヘッダー、エラー処理をコンポーネントへ直接書かないでください。

## UI

配置先は機能の責務で決めます。

- テーマに依存しない機能: `apps/web/src/lib/`配下
- テーマ固有の表示: `apps/web/src/lib/themes/`配下
- ページ全体に関わる機能: 対応するSvelteKit route
- アカウント向け機能: アカウント関連routeと共通lib

ディレクトリ構造はソースコードを正本とし、過去のテーマ構成を前提にしないでください。

## PWA

新機能はブラウザだけでなくPWAからも利用されます。

- standalone表示で操作できる
- safe areaでボタンが隠れない
- 更新後に古いキャッシュと致命的な不整合を起こさない
- オフライン時に保存済みと誤認させない
- 必要以上に初期バンドルを増やさない

## テスト

正常系だけでなく、入力境界、権限、存在しないID、関連データの整合性、閲覧専用状態への書き込みなどを確認します。

UIの計算は可能な限りpure functionへ分離し、主要操作はE2Eでも確認してください。
