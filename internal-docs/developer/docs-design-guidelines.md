# ドキュメントデザインガイドライン

このページは`docs/`全体の情報設計、文章、見た目の基準です。ユーザー向けガイドと開発者向けガイドの両方に適用します。

## 目的

- 必要な情報へ短い経路で到達できる
- 長く読んでも疲れにくい
- PC、スマートフォン、PWAから読みやすい
- 実装変更があっても古くなりにくい
- アクセシビリティを保つ

## 情報の鮮度

ドキュメントには現行仕様として必要な内容だけを記載します。

原則として、次は残しません。

- 過去仕様との比較や変更履歴
- 特定のPRやIssueで修正した経緯
- 移行作業だけに必要だった手順
- 削除済みの実装やテーブルの一覧
- 一時的な制限を恒久仕様のように書いた説明

履歴が必要な場合はGit履歴、Issue、Pull Requestを参照します。

## 正本を決める

変化しやすい一覧や値をドキュメントへ重複させないでください。

例:

- テーマ一覧: `apps/web/src/lib/themes/catalog.ts`
- DBスキーマ: `apps/db/migrations/sql/` と `apps/db/schema.sql`
- コマンド: 各`package.json`と`Makefile`
- CI・Preview・デプロイ: `.github/workflows/`
- PWA: `manifest.webmanifest`と`service-worker.ts`

ドキュメントには、利用者や開発者が判断するための考え方と参照先を記載します。

## 絵文字とアイコン

装飾目的の絵文字は原則として使用しません。見出し、リンク、表のラベルはテキストだけで意味が伝わるようにします。

アイコンが必要な場合は次の順で検討します。

1. テキストだけで表現できないか確認する
2. 既存のSVGアイコンを再利用する
3. 必要であればアクセシブルなSVGを追加する

SVGを使う場合は、装飾なら支援技術から隠し、意味を持つ場合は適切なラベルを付けます。

## PWAを前提にする

ユーザー向けガイドでは、普段使いの方法としてPWAを推奨します。

PWAの説明では、インストールの利点と、完全なオフライン編集ではないことを明確に分けて説明します。特定ブラウザのUI名称は変わる可能性があるため、必要以上に細部へ依存しません。

## 文章

- 1ページ1テーマを基本にする
- 冒頭で目的を説明する
- 操作手順は短い番号付き手順にする
- 実装詳細はユーザー向けページへ出しすぎない
- 更新時期に依存して意味が変わる表現を避ける
- 固定のURL、リソース名、バージョンは正本がある場合は参照に置き換える
- 注意書きは本当に判断が必要な箇所だけに使う

## 見た目

本文は読みやすい行長を優先し、強い装飾を増やしすぎません。見出し、余白、罫線、背景、文字の太さを使って情報階層を示します。

表やコードブロックは小さい画面でも内容が欠けないようにし、必要な場合は外側のラッパーで横スクロールできるようにします。

## アクセシビリティ

- 文字と背景のコントラストを確保する
- キーボードで操作できる
- `:focus-visible`を消さない
- アイコンだけの操作へアクセシブルネームを付ける
- 開閉状態を`aria-expanded`などで伝える
- 動きを減らす設定を尊重する
- 色だけで状態を伝えない

## 更新時のチェック

- 過去の経緯を書き足していないか
- 正本が別にある一覧を複製していないか
- 絵文字を装飾目的で追加していないか
- PWAの利用者が読んでも手順が成立するか
- モバイルで表、コード、ナビゲーションが読めるか
- リンク先が現行構成と一致しているか
